# 系统性能测试报告

**日期:** 2025年12月4日
**系统:** 分布式存储系统
**测试的 ADS 模式:** MPT (Merkle Patricia Trie), MEST, AccTrie (Accumulator Trie)

## 1. 执行摘要

本报告总结了分布式存储系统在三种不同的认证数据结构 (ADS) 模式下的性能基准测试结果：**MPT**、**MEST** 和 **AccTrie**。

基准测试评估了在增加、查询、更新和删除操作下的 **吞吐量** (每秒操作数) 以及证明生成和验证的 **延迟**。

**主要发现:**
*   **MEST** 实现了最高的吞吐量 (**860.27 ops/sec**) 和最快的证明验证时间，特别是在删除操作方面。
*   **MPT** 的表现与 MEST 非常接近，吞吐量为 **854.31 ops/sec**。
*   **AccTrie** 的性能明显较低，吞吐量为 **158.76 ops/sec** (约比 MEST/MPT 慢 5.4 倍)，且证明生成和验证的延迟要高得多。

## 2. 吞吐量对比

每次运行的总操作数: 4000 (1000次增加, 1000次查询, 1000次更新, 1000次删除)。

| ADS 模式 | 吞吐量 (ops/sec) | 相对性能 |
| :--- | :--- | :--- |
| **MEST** | **860.27** | **100% (基准)** |
| **MPT** | 854.31 | ~99.3% |
| **AccTrie** | 158.76 | ~18.5% |

## 3. 延迟分析

### 3.1 证明生成时间 (微秒 - µs)

数值越低越好。表示 `Storager` 生成加密证明所需的时间。

| 操作 | MPT (平均) | MEST (平均) | AccTrie (平均) |
| :--- | :--- | :--- | :--- |
| **增加 (Add)** | 887.03 µs | **842.55 µs** | 3564.38 µs |
| **查询 (Query)** | **179.86 µs** | 188.91 µs | 831.82 µs |
| **删除 (Delete)** | **270.36 µs** | 335.32 µs | 1133.33 µs |
| **更新 (Update)**\* | 1157.39 µs | 1177.87 µs | 4697.71 µs |

*\*注: 更新操作包含一次删除和一次增加，此处为两者平均耗时之和。*

### 3.2 证明验证时间 (微秒 - µs)

数值越低越好。表示 `Manager` (或客户端) 验证证明所需的时间。

| 操作 | MPT (平均) | MEST (平均) | AccTrie (平均) |
| :--- | :--- | :--- | :--- |
| **增加 (Add)** | 6.95 µs | **5.52 µs** | 27.89 µs |
| **查询 (Query)** | 6.80 µs | **4.76 µs** | 1075.46 µs |
| **删除 (Delete)** | 4.15 µs | **0.29 µs** | 21.23 µs |
| **更新 (Update)** | 12.41 µs | **6.61 µs** | 51.87 µs |

## 4. 详细观察

### MEST (基于 Merkle 的结构)
*   **优势:** 极佳的验证性能和最高的吞吐量。证明大小适中（比 MPT 小，但比 AccTrie 大）。
*   **劣势:** 无明显短板，是性能最均衡的选择。

### MPT (Merkle Patricia Trie)
*   **优势:** 吞吐量和延迟表现稳定，接近 MEST。
*   **劣势:** **证明大小最大**（约为 AccTrie 的 10 倍），这可能会在网络带宽受限的环境中成为瓶颈。

### AccTrie (累加器 Trie)
*   **优势:** **证明大小极小**。相比 MPT，其证明大小减少了约 90%。这使得它非常适合带宽昂贵或受限的场景（如移动设备、区块链轻客户端）。
*   **劣势:**
    *   **高计算开销:** 证明生成速度比 MPT/MEST 慢 3-4 倍。
    *   **查询验证慢:** 查询验证极其昂贵 (~1ms)，导致整体吞吐量较低。
    *   **总结:** AccTrie 是典型的“以时间换空间”方案。

## 5. 测试方法

*   **环境:** 本地回环 (127.0.0.1), Linux。
*   **工作负载:** 每种类型 1000 次顺序操作 (增加 -> 查询 -> 更新 -> 删除)。
*   **指标收集:** 在 Rust 服务处理程序中使用 `Instant::now()` 进行打点统计。
