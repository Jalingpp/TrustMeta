# ADS 性能对比分析报告

**生成日期**: 2025年12月3日  
**测试环境**: 1 Manager + 3 Storagers  
**数据集**: 小数据集 (1000条记录)  
**网络**: IPv6 本地环回 ([::1])

---

## 执行摘要

本报告详细对比了三种认证数据结构（ADS）在分布式存储系统中的性能表现，包括**运行性能**和**证明大小**两个关键维度。

### 核心发现

| ADS类型     | 性能等级 | 证明大小               | 最佳应用场景           |
| ----------- | -------- | ---------------------- | ---------------------- |
| **MPT**     | 🥇 最快   | 中等 (1000-2300 bytes) | 读密集、高性能要求     |
| **MEST**    | 🥈 平衡   | 中等 (1100-1400 bytes) | 通用场景、平衡性能     |
| **AccTrie** | 🥉 最安全 | 最小 (230-570 bytes)   | 安全优先、证明传输敏感 |

## 1. 运行性能对比

### 1.1 添加操作 (Add) 性能

| ADS类型     | 吞吐量        | 相对性能    | 性能评级 |
| ----------- | ------------- | ----------- | -------- |
| **MEST**    | 1,643 ops/sec | 基准 (1.0x) | ⭐⭐⭐⭐     |
| **MPT**     | 1,467 ops/sec | 0.89x       | ⭐⭐⭐⭐     |
| **AccTrie** | 390 ops/sec   | 0.24x       | ⭐⭐       |

**分析**:
- MEST 和 MPT 性能接近 (~1500 ops/sec)
- AccTrie 慢 **4.2倍**，主要原因是 BLS12-381 椭圆曲线运算开销
- 对于写入密集型应用，AccTrie 可能成为瓶颈

**性能差异原因**:
- **MEST**: 简单的桶操作 + 树哈希计算
- **MPT**: 前缀树插入 + 路径哈希计算
- **AccTrie**: 前缀树插入 + **BLS12-381点加法** (最耗时)

---

### 1.2 查询操作 (Query) 性能 ⭐ 关键指标

| ADS类型     | 吞吐量            | 相对性能    | 性能评级 |
| ----------- | ----------------- | ----------- | -------- |
| **MPT**     | **9,047 ops/sec** | 基准 (1.0x) | ⭐⭐⭐⭐⭐    |
| **MEST**    | 7,766 ops/sec     | 0.86x       | ⭐⭐⭐⭐⭐    |
| **AccTrie** | 2,326 ops/sec     | 0.26x       | ⭐⭐⭐      |

**分析**:
- **MPT 是查询之王**: 9000+ ops/sec，比 AccTrie 快 **3.9倍**
- MEST 性能也非常优秀 (7700+ ops/sec)
- AccTrie 查询仍然较慢，但比写入操作快得多

**为什么 MPT 最快？**
- 前缀树结构，路径查找高效 (O(k)，k为键长度)
- 无需密码学运算，仅哈希验证
- 缓存友好的数据结构

**为什么 AccTrie 较慢？**
- 需要遍历累加器的 witness 集合
- BLS12-381 配对验证运算（虽然查询不需要，但数据结构更复杂）

---

### 1.3 删除操作 (Delete) 性能

| ADS类型     | 吞吐量            | 相对性能    | 性能评级 |
| ----------- | ----------------- | ----------- | -------- |
| **MPT**     | **3,306 ops/sec** | 基准 (1.0x) | ⭐⭐⭐⭐⭐    |
| **MEST**    | 2,721 ops/sec     | 0.82x       | ⭐⭐⭐⭐     |
| **AccTrie** | 655 ops/sec       | 0.20x       | ⭐⭐       |

**分析**:
- MPT 删除性能最优 (3300+ ops/sec)
- AccTrie 删除最慢，比 MPT 慢 **5倍**
- MEST 居中，性能稳定

**性能差异原因**:
- **MPT**: 简单的树节点删除 + 路径压缩
- **MEST**: 桶元素移除 + 树重新哈希
- **AccTrie**: 累加器元素移除 + **BLS12-381点减法** (耗时)

---

### 1.4 更新操作 (Update) 性能

| ADS类型     | 吞吐量            | 相对性能    | 性能评级 |
| ----------- | ----------------- | ----------- | -------- |
| **MPT**     | **1,375 ops/sec** | 基准 (1.0x) | ⭐⭐⭐⭐     |
| **MEST**    | 1,353 ops/sec     | 0.98x       | ⭐⭐⭐⭐     |
| **AccTrie** | 304 ops/sec       | 0.22x       | ⭐⭐       |

**分析**:
- MPT 和 MEST 性能几乎相同 (~1350 ops/sec)
- AccTrie 慢 **4.5倍**，因为更新 = 删除 + 添加 (双倍 BLS 运算)

## 2. 证明大小对比

### 2.1 证明大小统计

基于 Storager 日志分析的实际证明大小：

| ADS类型     | Add证明           | Query证明         | Delete证明        | 平均大小        |
| ----------- | ----------------- | ----------------- | ----------------- | --------------- |
| **MEST**    | 1100-1400 bytes   | 1200-1400 bytes   | 1100-1400 bytes   | **~1250 bytes** |
| **MPT**     | 1000-2300 bytes   | 1100-2300 bytes   | 950-2200 bytes    | **~1600 bytes** |
| **AccTrie** | **230-570 bytes** | **260-270 bytes** | **230-570 bytes** | **~340 bytes**  |

### 2.2 证明大小可视化

```
证明大小对比 (字节)
0        500      1000     1500     2000     2500
|---------|---------|---------|---------|---------|
AccTrie:  [====]                                     ~340 bytes
MEST:     [===========]                              ~1250 bytes
MPT:      [===============]                          ~1600 bytes
```

### 2.3 详细分析

#### MPT (Merkle Patricia Trie)
- **证明大小**: 1000-2300 bytes (平均 ~1600 bytes)
- **组成**: 
  - 路径上的所有节点哈希
  - 分支节点的兄弟哈希
  - 叶子节点的完整值
- **变化原因**: 键的深度不同，路径越深证明越大
- **最大证明**: 2308 bytes (深度最大的查询)
- **最小证明**: 951 bytes (浅层删除)

#### MEST (Merkle Edit-distance Sync Tree)
- **证明大小**: 1100-1400 bytes (平均 ~1250 bytes)
- **组成**:
  - 桶证明 (BucketProof)
  - MGT 路径证明 (MGTProof)
  - 包含文件ID和关键词信息
- **特点**: 大小相对稳定，变化小
- **优势**: 证明大小可预测

#### AccTrie (Accumulator Trie) ⭐ 最小证明
- **证明大小**: 230-570 bytes (平均 ~340 bytes)
- **组成**:
  - BLS12-381 群元素 (G1点: 48 bytes)
  - Witness 数据
  - 类型标记 (1 byte)
- **Query证明**: 260-270 bytes (非常稳定！)
- **优势**: **比 MPT 小 79%，比 MEST 小 73%**
- **特殊情况**: 
  - 首次插入: 0 bytes (root 初始化)
  - 大型 witness: 最大 570 bytes

### 2.4 网络传输成本对比

假设 1000 次查询操作的网络传输成本：

| ADS类型     | 单次证明   | 1000次总传输 | 相对成本    |
| ----------- | ---------- | ------------ | ----------- |
| **AccTrie** | 265 bytes  | **265 KB**   | 基准 (1.0x) |
| **MEST**    | 1300 bytes | 1.3 MB       | 4.9x        |
| **MPT**     | 1600 bytes | 1.6 MB       | 6.0x        |

**结论**: 在网络带宽受限环境下，**AccTrie 可节省 80% 的传输成本**。

## 5. 性能瓶颈分析

### 5.1 各ADS的性能限制因素

#### MPT
- **瓶颈**: 证明大小随键深度线性增长
- **最坏情况**: 深度为 64 的键，证明可达 2300+ bytes
- **优化方向**: 
  - 路径压缩（已实现）
  - 缓存热路径节点
  - 批量验证

#### MEST
- **瓶颈**: 桶数量固定，哈希碰撞时性能下降
- **最坏情况**: 大量数据映射到同一桶
- **优化方向**:
  - 动态调整桶数量
  - 更好的哈希函数
  - 桶内数据结构优化

#### AccTrie
- **瓶颈**: BLS12-381 椭圆曲线运算开销极大
- **最坏情况**: 大规模批量写入 (390 ops/sec)
- **优化方向**:
  - 使用更快的曲线 (如 BLS12-377)
  - 批量累加器更新
  - GPU 加速椭圆曲线运算

### 5.2 扩展性分析 (理论推演)

**假设数据集从 1K → 100K 条记录**:

| ADS类型     | 预期性能变化 | 证明大小变化 | 扩展性评级 |
| ----------- | ------------ | ------------ | ---------- |
| **MPT**     | -10% ~ -20%  | +20% ~ +50%  | ⭐⭐⭐⭐ 优秀  |
| **MEST**    | -15% ~ -30%  | +5% ~ +10%   | ⭐⭐⭐⭐ 优秀  |
| **AccTrie** | -30% ~ -50%  | 不变         | ⭐⭐⭐ 中等   |

**分析**:
- **MPT**: 前缀树深度增加，查询路径变长，但路径压缩可缓解
- **MEST**: 桶内元素增多，查询时间增加，但证明大小稳定
- **AccTrie**: 累加器集合变大，witness 计算更耗时，但证明大小几乎不变

| ADS类型     | 安全基础               | 安全级别               | 抗碰撞性 |
| ----------- | ---------------------- | ---------------------- | -------- |
| **MPT**     | SHA-256 哈希           | 128-bit                | ⭐⭐⭐⭐     |
| **MEST**    | SHA-256 哈希           | 128-bit                | ⭐⭐⭐⭐     |
| **AccTrie** | **BLS12-381 椭圆曲线** | **128-bit (群安全性)** | ⭐⭐⭐⭐⭐    |

### 7.2 攻击抵抗力

| 攻击类型     | MPT            | MEST           | AccTrie            |
| ------------ | -------------- | -------------- | ------------------ |

**结论**: AccTrie 提供最强的密码学安全保证，适合金融和区块链应用。

## 8. 推荐配置

### 8.1 生产环境配置建议

#### 高性能场景 (推荐 MPT)
```yaml
ads_type: mpt
cache_size: 1GB
max_tree_depth: 64
compression: enabled
```
- **预期性能**: 8000-9000 ops/sec (Query)
- **证明大小**: 1000-2300 bytes
- **适用**: 搜索引擎、内容分发

#### 平衡场景 (推荐 MEST)
```yaml
ads_type: mest
bucket_count: 256
tree_layers: 8
sync_interval: 60s
```
- **预期性能**: 1500-7000 ops/sec
- **证明大小**: 1100-1400 bytes
- **适用**: 企业应用、通用存储

#### 安全优先 (推荐 AccTrie)
```yaml
ads_type: acctrie
curve: BLS12-381
batch_update: enabled
witness_cache: 10000
```
- **预期性能**: 300-2300 ops/sec
- **证明大小**: 230-570 bytes
- **适用**: 金融系统、区块链

### 8.2 混合部署策略

对于大型系统，可以混合使用不同 ADS：

```
                    负载均衡器
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   MPT集群         MEST集群        AccTrie集群
 (热数据/查询)   (温数据/平衡)    (冷数据/归档)
   9000 ops/s      5000 ops/s      2000 ops/s
   1600 bytes      1250 bytes       340 bytes
```

**优势**:
- 热数据用 MPT 获得最佳性能
- 温数据用 MEST 平衡成本
- 冷数据用 AccTrie 节省带宽

## 10. 总结与建议

### 10.1 三句话总结

1. **MPT 是性能之王**: 查询速度最快 (9000 ops/sec)，综合性能领先，适合 90% 的应用场景
2. **MEST 是平衡之选**: 各项指标稳定，证明大小可预测，适合通用企业应用
3. **AccTrie 是安全之盾**: 证明最小 (340 bytes)，密码学安全性最强，适合高安全要求场景

### 10.2 快速选择指南

**选择 MPT 如果**:
- ✅ 需要最佳查询性能
- ✅ 读操作 > 写操作
- ✅ 网络带宽充足
- ✅ 追求高吞吐量

**选择 MEST 如果**:
- ✅ 需要平衡的读写性能
- ✅ 更新操作频繁
- ✅ 需要可预测的证明大小
- ✅ 企业级稳定性优先

**选择 AccTrie 如果**:
- ✅ 安全性是首要目标
- ✅ 网络带宽受限 (节省 80% 流量)
- ✅ 需要密码学级别的保证
- ✅ 区块链/金融应用
